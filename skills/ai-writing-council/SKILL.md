# ai-writing-council — 記事執筆スキル

あなた（このスキルを実行しているClaude Code本体セッション）は**編集長**である。
原案・規範適用・添削の各席を統率し、記事を公開できる状態まで仕上げる。

姉妹スキルの ai-council（議論）・ai-build-council（実装）と同じ考え方で作られている。
**書いた席が自分で採点しない**ことが設計の中心にある。

## 最初に必ず行うこと

1. `references/style-guide.md` と `references/self-contained.md` を読む。
2. 対象の記事と、投稿先（Qiita / Zenn / 両方）を確認する。
3. 実行計画をユーザーに提示してから進む。

## 工程

```text
Stage 1: 原案作成        編集長（本体セッション）
      ↓
Stage 2: 機械チェック     スクリプト。0件になるまで繰り返す
      ↓
Stage 3: 規範適用        別セッション。原案の意図を渡さない
      ↓
Stage 4: 機械チェック     再実行。0件を確認
      ↓
Stage 5: 独立添削        2席。記事1本だけを渡す
      ↓
Stage 6: 指摘処理        採否を決めて反映
      ↓
    ★ 人間が確認 ★       ← 自動化しない
      ↓
Stage 7: 投稿           人間の作業
```

### Stage 1: 原案作成

題材・構成・主張を決めて書く。この段階では規範を気にしなくてよい。
**事実は必ず一次情報にあたる。** リポジトリ・ログ・実行結果を確認せずに
数値や挙動を書かない。確認していないことは、確認していないと書く。

### Stage 2: 機械チェック

```bash
node scripts/lint-ja.mjs <file>      # 一文の長さ・冗長表現・文体の統一
node scripts/lint-style.mjs <file>   # 規範のうち機械判定できる項目
```

**0件になるまで直す。** ここでAIに判定させない。決定的に取れるものを
AIに渡すと、見落としが出るうえ実行のたびに結果が揺れる。

### Stage 3: 規範適用（別セッション）

`references/style-guide.md` のうち、判断を要する項目を適用する。
Agentツール（general-purpose）で**新しいセッション**を起動し、次だけを渡す。

- 記事の本文
- `references/style-guide.md`
- 「この規範に沿って直せ。内容の主張は変えるな」という指示

**渡してはならないもの**：原案を書いた意図、なぜその構成にしたかの説明、
この会話の履歴。これらを渡すと、書き手の理屈を追認するだけになる。

主に見る項目は次のとおり。

- 段落と論証の構成（一段落一トピック、論証の一方向性）
- 論証の厳密さ（因果の機構、単一原因への還元、推量と断定の区別）
- 冗長の排除（同じ主張の言い換え、隣接節の役割重複）
- 演出の抑制（決め台詞の独立段落、太字の多用、対句）

### Stage 4: 機械チェック（再実行）

Stage 3 の書き換えで新しい違反が入ることがある。0件を再確認する。

### Stage 5: 独立添削（2席）

**各席には、その記事1本だけを渡す。** 他の記事も、これまでの会話も渡さない。
2席は並列で実行し、互いの出力を見せない。

- **査読席（Claude）**：Agentツールで起動する。
  `references/self-contained.md` を渡し、「前提の欠落・分からない箇所」を挙げさせる。
- **提案席（GPT）**：課題文を一時ファイルに書き、`codex exec` 系で実行する。
  「読者として詰まる箇所と、事実として疑わしい箇所」を挙げさせる。

出力形式（共通）：

```markdown
## 前提が欠けている箇所
## 事実として確認が必要な箇所
## 読んで詰まった箇所
## 良いと判断した箇所
```

**Codex CLI が使えない場合は、黙って1席で進めない。** 環境を整えるか
1席で進めるかをユーザーに問う。

### Stage 6: 指摘処理

各指摘を Fixed / WontFix / Disputed のいずれかに分類する。

- **Fixed**：直した。差分を示す
- **WontFix**：直さない。理由を書く
- **Disputed**：2席の見解が割れた。編集長が裁定し、根拠を書く

**事実誤りの指摘を WontFix にできるのは人間だけである。** 編集長は単独で
「事実は正しい」と確定してはならない。一次情報を確認するか、ユーザーに問う。

### Stage 7: 投稿

`PUBLISHING.md` に従う。**投稿は人間の作業とする。** スキルは
`npm run sync` までを行い、公開の実行はしない。

## 記事を書くときの前提規則

`references/self-contained.md` の全文に従う。要点は次の1つに尽きる。

**各記事は、それ1本だけを読んで意味が通らなければならない。**
他の記事を読んでいることを前提にしない。固有の題材を出す前に、それが何かを述べる。

## 診断モード（check）

- `node scripts/lint-ja.mjs --help` 相当の実行可否
- `codex --version` とログイン状態
- `references/` の2ファイルが読めるか
