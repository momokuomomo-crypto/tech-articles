案出し編で出た55案のうち、実装して[Chromeウェブストアに公開](https://chromewebstore.google.com/detail/pcgbpaagcljfakbhmoiaoekmfbfdfpob)した1本の話です。

作ったもの：**和暦変換（改元日対応）**（2026-08-05公開）

この記事は前半が「何を作ったか・なぜ作ったか」、後半が「和暦を実装して分かった落とし穴」です。後半は和暦を扱うすべての実装者に効く内容なので、拡張に興味がなくてもそこだけ読めます。

## 何を作ったか

西暦と和暦を日付単位で相互変換するChrome拡張です。

```
入力：1989/1/8

  平成元年1月8日
  1989年1月8日
  ※ 1989年は1月7日までが昭和64年、1月8日からが平成元年
```

## なぜこれを選んだか

55案から1本を選ぶとき、AIに「どれが良いか」を選ばせていません。3案に絞ったうえで、こういうゲートを通しました。

> 3候補について競合調査とストア掲載文を作り、**人間が「自分ならインストールするか」を判定**してから1件だけ着手する

掲載文を先に書くと、その拡張が何の問題を解くのか、既存のものと何が違うのかが実装前にはっきりします。書けなければ、その案は弱いと判断できます。

査読席はこの案をこう評価していました。

> 日本固有の問題であり、英語圏製の拡張が構造的に参入しない

## 既存の和暦変換ツールとの違い

和暦変換のツールはすでにあります。差別化点は1つに絞りました。

**改元のあった年は、境界日を注記で示す。**

同じ1989年でも、1月7日までは昭和64年、1月8日からは平成元年です。多くの変換ツールは「1989年 → 平成元年」と答えて終わりますが、これは1月1日〜7日について**間違い**です。

### 存在しない和暦は作らない

`昭和64年1月8日` は存在しません。昭和は1月7日で終わっているからです。

この拡張は、そういう入力に対して**存在しない和暦を作りません。** 期間外であることを示したうえで「この日付は 平成元年1月8日 です」と正解を併記します。

あたりまえに見えるかもしれません。しかし後述するとおり、**Javaの標準ライブラリですら、デフォルト設定では `昭和64年1月8日` を例外なしに `平成元年1月8日` へ黙って書き換えます。** 黙って直すのと、間違いを指摘したうえで正解を出すのは別のことです。

### 表記ゆれを吸収する

実際にコピペされる文字列は綺麗ではありません。以下をすべて受理します。

```
1989/1/8        19890108        1989年1月8日
平成元年1月8日   H1.1.8          H1年1月8日
H元/1/8         西暦1989年1月8日  １９８９年１月８日（全角）
生年月日：1989年1月8日            1989年1月8日（日）
```

`生年月日：` のような先頭ラベル付きと `（日）` のような曜日付きに対応しているのは、**実際の入力がそういう形をしているから**です。

年だけでも変換できます。`1901` は明治34年。改元のあった年は両方を境界つきで並べます。

# ここからが本題：和暦の元号境界は「1日ずれる」だけでは済まない

ここからは実装して分かった落とし穴です。和暦のバグは、たいてい「元号が切り替わる日」の周辺で起きます。しかも厄介なことに、その多くは**例外を投げずに、間違った値を返す**タイプです。

以下はすべて **OpenJDK 21 の `java.time.chrono.JapaneseDate` で実際に動かして確認**しました。

## 前提：近代5元号の境界

| 元号 | 開始 | 終了 |
|---|---|---|
| 明治 | 1868-10-23 | 1912-07-30 |
| 大正 | 1912-07-30 | 1926-12-25 |
| 昭和 | 1926-12-25 | 1989-01-07 |
| 平成 | 1989-01-08 | 2019-04-30 |
| 令和 | 2019-05-01 | — |

開始日と終了日が**同じ日で重なっている**箇所があります。これが落とし穴2です。

## 落とし穴1：昭和64年は7日間しかない

昭和天皇の崩御が1989-01-07、翌日から平成です。**昭和64年は1月1日から1月7日までの7日間しか存在しません。**

```
1989-01-01 -> Showa 64-01-01
1989-01-07 -> Showa 64-01-07
1989-01-08 -> Heisei 1-01-08
```

元年が短いのは昭和だけではありません。

- **昭和元年**：7日間（1926-12-25〜12-31）
- **大正元年**：約5か月
- **令和元年**：8か月

「元号の1年目は12か月ある」という前提でテストデータを作ると、この7日間は永久にテストされません。

## 落とし穴2：崩御による改元は「同じ日が2つの元号を持つ」

**改元のルールが時代によって違います。**

- **明治→大正（1912-07-30）と大正→昭和（1926-12-25）**：旧制度の「践祚即日改元」。崩御したその日のうちに改元されるため、**同じ1日が新旧2つの元号で表現されます**。1926-12-25 は「大正15年12月25日」でもあり「昭和元年12月25日」でもある
- **昭和→平成（1989-01-07/08）**：元号法（1979年）下では政令の施行が翌日。重複しない
- **平成→令和（2019-04-30/05-01）**：崩御ではなく譲位。重複しない

**重複が起きるのは1912年と1926年の2日だけ**です。

JDKはこの重複を片方に寄せています。

```
大正15年12月25日 -> REJECTED (year, month, and day not valid for Era)
昭和1年12月25日  -> 1926-12-25
```

歴史的には「大正15年12月25日」が正しい表記なのに、JDKはパースを拒否します。古い戸籍や登記簿から取り込んだデータにこの表記が入っていると、そこだけ落ちます。

## 落とし穴3：デフォルトのパーサは存在しない日付を黙って書き換える

**この記事で一番言いたいのはここです。**

存在しない「昭和64年1月8日」をJDKに食わせると、`ResolverStyle` によって挙動が3通りに割れます。

```
STRICT   -> REJECTED (DateTimeParseException)
SMART    -> Heisei 1-01-08
LENIENT  -> Heisei 1-01-08
```

`DateTimeFormatter.ofPattern()` の**デフォルトは SMART** です。つまり何も指定しなければ、**存在しない日付が例外なしに平成元年1月8日へ黙って書き換えられます。**

入力バリデーションのつもりでパースしているなら、これは検知漏れです。**和暦をパースするときは必ず `ResolverStyle.STRICT` を明示してください。**

```java
DateTimeFormatter f = DateTimeFormatter.ofPattern("GGGGy年M月d日")
    .withChronology(JapaneseChronology.INSTANCE)
    .withLocale(Locale.forLanguageTag("ja-JP-u-ca-japanese"))
    .withResolverStyle(ResolverStyle.STRICT);   // ← これを忘れない
```

この拡張が「存在しない和暦を作らない」と謳っているのは、まさにこの挙動を避けるためです。

## 落とし穴4：「元年」は自動では出力されない

正式な表記は「令和1年」ではなく「令和元年」ですが、JDKは元年を知りません。

```
pattern GGGGy年M月d日   2019-05-01 -> 令和1年5月1日
pattern GGGGyy年M月d日  2019-05-01 -> 令和01年5月1日
```

出力側で「年が1なら元年に差し替える」処理を自分で書く必要があります。入力側では「元年」と「1年」の両方を受け付ける必要があります。表示と保存で表記が揺れると、文字列比較での突き合わせが壊れます。

## 落とし穴5：明治5年12月3日〜30日は存在しない

明治政府は改暦（天保暦→グレゴリオ暦）を行い、**明治5年12月2日の翌日を明治6年1月1日**としました。明治5年12月3日から12月30日までの28日間は、暦の上で存在しません。

この改暦のせいで、JDKは明治6年より前を扱えません。

```
1868-01-01 -> EXCEPTION: JapaneseDate before Meiji 6 is not supported
1872-12-02 -> EXCEPTION: JapaneseDate before Meiji 6 is not supported
1873-01-01 -> Meiji 6-01-01   ← ここが下限
```

`JapaneseChronology.INSTANCE.range(ChronoField.YEAR)` も `1873 - 999999999` を返します。

この拡張が「1873年1月1日以降のみ対応」と制限を明記しているのは、この理由です。明治5年以前は旧暦のため、元号年から西暦への機械換算がそもそも成立しません。

## 落とし穴6：新元号は事前に分からない

令和の発表は2019-04-01、施行は5月1日。**猶予は1か月**でした。次も同じとは限りません。

元号をenumやswitch文にハードコードしていると、改元のたびにコード修正と再デプロイが必要になります。

JDKには将来元号を試す仕組みがあります。システムプロパティ `jdk.calendar.japanese.supplemental.era` で仮の元号を追加できます。

```bash
java -Djdk.calendar.japanese.supplemental.era="name=Tester,abbr=T,since=1924992000000" App
```

`since` はエポックミリ秒（上の例は2031-01-01起点）。実際に動かすと：

```
# 指定なし
eras known: [Meiji, Taisho, Showa, Heisei, Reiwa]
2031-03-01 -> Reiwa 13-03-01

# 指定あり
eras known: [Meiji, Taisho, Showa, Heisei, Reiwa, Tester]
2031-03-01 -> Tester 1-03-01
```

**改元前に、改元後の挙動をCIで検証できます。**

### この拡張ではどう扱ったか

同梱の元号データには「ここまでは正しいと確認した」という期限があります。それを超える日付をどうするか、設計段階で判断が割れました。

当初の設計は「**変換を止める**」でした。正確さを優先した判断です。査読側はこれに反対し、**失敗の非対称性**を根拠に挙げました。

| | 誤変換のリスク | 停止のコスト |
|---|---|---|
| 発生条件 | 改元が**起きたとき**、改元日以降の日付のみ | 改元が**起きなくても**、期限以降のすべての日付 |
| 影響範囲 | 限定的 | 全面的 |

確認期限はビルド時に凍結される値です。更新が止まれば、時間が経つだけで「**今日の日付が変換できない和暦変換拡張**」ができあがります。

結論として、変換は続行して警告注記を付す形に変更しました。決め手は形式の一貫性です。この拡張全体は「**事実は主表示、不確かさは注記**」で統一されています。確認期限だけが「停止」という強い扱いを取る理由がありません。

## 最低限入れておきたいテストケース

境界そのものと、その前後1日を必ず含めます。

| 日付 | 期待 |
|---|---|
| 1873-01-01 | 明治6年1月1日（ライブラリ下限） |
| 1912-07-29 / 07-30 | 明治45年 / 大正元年（同日重複あり） |
| 1926-12-24 / 12-25 | 大正15年 / 昭和元年（同日重複あり） |
| 1926-12-31 | 昭和元年12月31日（元年は7日間） |
| 1989-01-07 / 01-08 | 昭和64年 / 平成元年 |
| 2019-04-30 / 05-01 | 平成31年 / 令和元年 |
| 「昭和64年1月8日」 | **STRICTで例外**（SMARTだと平成元年に化ける） |
| 「令和元年5月1日」 | 元年表記のパース |
| 1872-12-15 | 存在しない日（改暦の空白） |

# 実装と公開

## 権限を3つに絞った

```
contextMenus, storage, notifications
```

これだけです。**ページの内容を読み取る権限（`host_permissions`・`activeTab`・`scripting`）は要求せず、外部通信も一切行いません。**

権限を絞ったのは審査対策でもあります。拡張の権限が増えるほど、なぜ必要かの説明が求められ、審査が長引きます。

ビルド成果物の検査を自動化して、**外部URL参照・`eval`・`new Function`・想定外の権限・`host_permissions` の混入を機械的に弾く**ようにしました（`npm run verify`）。うっかり増えたらビルドが落ちます。

## テストは152件

```
npm test        # 単体・統合テスト（152件）
npm run verify  # ビルド → dist の検査
```

最初の自動テストは99件でした。**53件の増分は、実機で見つかった6件の不具合の回帰テストと、後から足したポップアップの結合テスト**です。

自動テスト99件が通った状態で実機のChromeに載せたら6件出た、という話は実装編に詳しく書きました。うち2件は**要件そのものの誤り**で、テストは要件を正しく反映していました。

## ストア提出で気をつけたこと

掲載情報の下書きに、冒頭からこう書きました。

> **この拡張は外部通信を一切行わず、データを一切収集しない**ため、どの欄も「収集しない」で一貫させる。事実と異なる申告をすると審査で差し戻される。

データ収集の申告欄は実装と食い違うと差し戻されます。**先に「収集しない」で全部埋まる設計にしておく**のが結局いちばん速い、という判断でした。

概要文は132文字以内の制限に対して71文字に収めています。

> 西暦と和暦を日付単位で相互変換します。改元のあった年は境界日を注記で示し、昭和64年1月8日のような存在しない和暦は作りません。外部送信なし。

差別化点（境界日を示す）と、具体例（昭和64年1月8日）と、安心材料（外部送信なし）を1文ずつ入れました。

## 制限事項を先に書く

READMEにもストア掲載文にも明記しました。

- **1873年1月1日（明治6年1月1日）以降**のみ対応（落とし穴5）
- 元号データの確認期限を超える日付も変換するが、**改元があった場合は正しい和暦が異なる旨の注記**が付く（落とし穴6）
- 右クリックの結果はChromeの通知に表示する。OS側で通知が抑制されている場合は検知できない。その場合はポップアップに結果が残る

## まとめ

拡張として：

- **改元境界を能動的に教える**のが差別化点
- **存在しない和暦を作らない**。黙って直さず、間違いを指摘して正解を出す
- **権限3つ・外部通信ゼロ**。申告欄が全部「収集しない」で埋まる設計にする

和暦の実装として：

- 元号の1年目は12か月あるとは限らない。**昭和64年と昭和元年は7日間**
- **1912-07-30 と 1926-12-25 は、同じ日が2つの元号を持つ**
- **パースは `ResolverStyle.STRICT` を明示する**。デフォルトのSMARTは存在しない日付を黙って書き換える
- **「元年」は自前で処理する**
- **明治6年（1873-01-01）より前は標準ライブラリの範囲外**
- **次の改元は `jdk.calendar.japanese.supplemental.era` で先に試せる**

和暦のバグは、境界の1日を踏むまで表に出てきません。境界日をテストに固定してしまうのが一番効きます。
