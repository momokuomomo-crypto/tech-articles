AIを開発に使うとき、ひとつのセッションにすべてを任せるのをやめました。役割を分けて、複数のチェックを通す仕組みを作っています。

道具は2つ作りました。何を作るかを決める**議論役**と、どう作るかを決めて実装する**実装役**です。どちらもClaude Codeのスキルとして書きました。この2つを通して、Chrome拡張を1本、Chromeウェブストアまで出しています。作ったのは西暦と和暦を相互変換する拡張です。

使うのはClaude Code（サブスクリプション）とCodex CLI（ChatGPTプラン）の2つだけです。APIの従量課金は使っていません。

## 全体の流れ

```text
 テーマ「Chrome拡張で何を作るか」
        │
        ▼
┌───────────────────────┐
│ 議論役                 │  議長・提案・査読の3席
│ 何を作るかを決める      │  独立意見 → 相互レビュー → 統合・裁定
└───────────────────────┘
        │  稟議書（裁定つき）
        ▼
    ★ 人間が承認 ★
        │
        ▼
┌───────────────────────┐
│ 実装役                 │  Stage 0〜7、工程ごとにゲート
│ 設計・実装・レビュー     │
└───────────────────────┘
        │  動くコード
        ▼
    ★ 人間が実機確認 ★
        │
        ▼
   Chromeウェブストア公開
```

## なぜ役割を分けるのか

ひとつのAIに案を出させれば、質の高い案が返ってきます。ただし、その案に反論する相手がいません。同じセッションに検算させても、同じ前提の上をもう一度通ることになります。

そこで、別のセッション、できれば別のモデルに、前の出力を見せずに検討させます。前提を共有していない相手が読むと、ひとつでは出てこない指摘が出ます。

議論役は3席に分けました。

| 席 | モデル | 役割 |
|---|---|---|
| 議長 | Claude Fable | 論点整理・統合・裁定 |
| 提案 | GPT（Codex CLI） | 実現案・技術選定・具体策 |
| 査読 | Claude（サブエージェント） | 前提・リスク・矛盾・欠落の指摘 |

対等な3社を並べるのではなく、役割で非対称にしています。提案席は前に進める係、査読席は止める係、議長は決める係です。

もっとも気を使ったのは**独立性**です。各席には課題文だけを渡し、他席の出力も議長自身の見解も見せません。先に片方の意見を見せると、もう片方がそれに引きずられ、独立したチェックになりません。

裁定では多数決を使わないことにしました。2席が同じ結論に達しても、それだけでは正しさの根拠になりません。目的適合性・制約充足・根拠の強さ・リスクの4観点で、どの主張をなぜ採ったかを議長が書き残します。

## 分けた効果が出た例

実装工程で、査読席の指摘が提案席の中核設計をひっくり返しました。

論点は、同梱の元号データの確認期限を超える日付をどう扱うかです。提案席は変換を止める設計を出しました。正確さを優先した、筋の通った判断です。

査読席はこれに反対し、根拠として**失敗の非対称性**を挙げました。

| | 誤変換のリスク | 停止のコスト |
|---|---|---|
| 発生条件 | 改元が起きたとき、改元日以降の日付のみ | 改元が起きなくても、期限以降のすべての日付 |
| 影響範囲 | 限定的 | 全面的 |

確認期限はビルド時に凍結される値です。したがって更新が止まれば、時間の経過だけで、今日の日付が変換できない和暦変換拡張ができあがります。議長は査読席の主張を採りました。

この判断は多数決では通りませんでした。役割を分けたことが、そのまま設計の質になっています。

査読席はさらに、流用元の実コードまで読みに行きました。設計書は無警告で令和XX年を返す設計を採らないと宣言しています。ところが、コピーしてくる予定のコードは `WAREKI_DISPLAY_HORIZON_YEARS = 100` を持ち、2119年まで令和101年を無警告で返す実装でした。設計書だけを読んでいては出ない指摘です。

## 2つのツールをつなげない

議論役と実装役は、コード上でつながっていません。連携はファイルを渡すだけです。

つなげない理由は、間に人間の承認を置くためです。稟議書が出た直後に実装が始まると、承認する時間がなくなります。

実装役は議論役の結論を前提としても扱いません。実装役のREADMEにはこう書いています。

> ai-councilの成果物をそのまま採用することは目的としない。

実装側は独自に設計し直します。ここでも見ているのは、同じ結論に別のルートから到達するかどうかです。

## 工程を定義しておく効果

実装役は工程を Stage 0 から 7 まで定義し、到達状況を `state.json` に記録します。

```json
"not_done": [
  "Stage 5: 固定diffの独立実装レビュー（2席）",
  "Stage 6: 指摘処理・Test Gate B"
],
"note": "Stage 0-4 まで完了。実機で動作確認した者はまだ居ない。"
```

公開した拡張は、Stage 5 を飛ばしています。

ここで効いているのは、飛ばした事実が記録に残る仕組みです。工程を定義していなければ、レビュー済みかどうか自体が曖昧なまま残ります。定義してあるので、何が済んで何が済んでいないかを、後から読んで判断できます。

同じ考えを各席の出力形式にも入れました。相互レビューでは、未解決の論点を返させ、なければ「なし」と明記させます。書かせないかぎり、触れていないのか、無いのかを区別できません。

## 回してみた結果

| 項目 | 結果 |
|---|---|
| 会合の回数 | 3回 |
| 出た案の総数 | 55件（稼働キュー37、候補プール18） |
| ストア公開まで到達 | 5件 |

案出しは期待どおりに回りました。3席に投げれば1回の会合で30案出ます。案が足りなくなることはありません。

面白かったのはその先です。実装は済んでいるのに提出していない在庫が積み上がったとき、提案席と査読席が独立に同じ結論へ達しました。新規案をこれ以上積み増すべきではない、という結論です。

独立した2席が同じ結論に達したので、この主張は採りました。効いた対策は、完了の定義を変えたことです。

> 完了 ＝ Chromeウェブストアで公開完了。実装完了・提出準備完了は成功指標として0点で数える。

実装完了を数えるのをやめると、在庫は成果ではなく、片付けるべきものとして見えるようになりました。

## チェックの種類と回数

実装工程で、自動テスト99件を通過したコードを実機のChromeに載せたところ、6件の不具合が見つかりました。内訳は次のとおりです。

- 2件は要件そのものの誤り。テストは要件を正しく反映していた
- 1件はモックが実機の挙動を持たない領域
- 1件はCSSで、テストの対象外
- 1件はテストが1件も存在しない層

自動テストは要件と実装の一致を見る仕組みです。したがって要件のほうが間違っていれば、正しく動いていることを確認し続けます。この6件でテストの件数を増やしても、2件は見つかりません。

見つけたのは、実機で触るという別種のチェックでした。同じ観点のチェックを3回かけても、通るものは3回とも通ります。チェックは回数ではなく種類を増やすと効く、というのが実際に回して分かったことです。

6件はすべて修正し、回帰テストを追加しました。テストは99件から152件に増えています。
