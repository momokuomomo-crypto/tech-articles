AIを仕事に使うようになって、チェックの仕組みを自分で作ることにしました。その記録です。

きっかけは、職務経歴書をAIに書かせたときでした。

## `＜要記入＞` が残っていた

AIが返してきた職務経歴書には、こういう欄が並んでいました。

```
【プロジェクト概要】
＜要記入：システムの目的・対象業務・規模などを記載＞

【実績・取り組み】
・＜要記入＞
```

構造は作られていて、こちらが伝えた事実（時期・役割・使った言語）は埋まっている。**そして、伝えていないことは埋まっていませんでした。**

これを見て、逆のことを考えました。

**もしここに、もっともらしい実績が書かれていたらどうなっていたか。**

「運用改善により障害対応時間を30%削減」くらいの文であれば、職務経歴書として自然に読めます。自分の経歴なので明らかな嘘なら気づきますが、**細部が少しずれた程度なら、気づかないまま提出していた可能性が高い。**

ここが怖いところだと思いました。AIの出力で本当に危険なのは、間違っていることではありません。

> **埋まっているものと、確認されたものが、見た目で区別できないこと。**

空欄なら気づきます。「たぶんこうだろう」で埋められた文章は、気づけません。

## 方針を2つ決めた

そこで、AIに何かをさせるときの方針を2つ立てました。

**1. 独立したチェックを複数かける。** 1つのAIに書かせて同じAIに検算させても、同じ思い込みを二度通るだけです。**別のセッション、できれば別のモデル**に、前の出力を見せずに検討させる必要があります。

**2. 分からないことを「分からない」と書かせる。** `＜要記入＞` と同じことです。未確認の箇所を未確認だと明示させないと、確認済みの箇所と混ざります。

この2つを毎回手でやるのは続きません。**仕組みにしました。**

## 作ったもの

役割の違う2つのClaude Codeスキルを作り、実際に1本のアプリを作って公開するところまで回しました。

| | 役割 | 記事 |
|---|---|---|
| [ai-council_v2](https://github.com/momokuomomo-crypto/ai-council_v2) | 何を作るかを決める（議論・意思決定） | 案出し編 |
| [ai-build-council](https://github.com/momokuomomo-crypto/ai-build-council) | どう作るかを決めて実装する | 実装編 |
| [chrome-ext-wareki-converter](https://github.com/momokuomomo-crypto/chrome-ext-wareki-converter) | 実際に作って公開したもの | アプリ編 |

```text
 テーマ「Chrome拡張で何を作るか」
        │
        ▼
┌───────────────────────┐
│ ai-council_v2         │  議長・提案・査読の3席
│ 何を作るかを決める      │  独立意見 → 相互レビュー → 統合・裁定
└───────────────────────┘
        │  稟議書（裁定つき）
        ▼
    ★ 人間が承認 ★        ← ここは自動化しない
        │
        ▼
┌───────────────────────┐
│ ai-build-council      │  Stage 0〜7、工程ごとにゲート
│ 設計・実装・レビュー     │
└───────────────────────┘
        │  動くコード
        ▼
    ★ 人間が実機確認 ★    ← ここも自動化しない
        │
        ▼
   Chromeウェブストア公開
```

### 「独立したチェック」を形にする

`ai-council` は3席で議論させます。

| 席 | 役割 |
|---|---|
| 議長 | 論点整理・統合・裁定 |
| 提案 | 実現案・技術選定・具体策 |
| 査読 | 前提の誤り・リスク・矛盾・欠落の指摘 |

対等な3社ではなく、**役割で非対称**にしています。提案席は前に進める係、査読席は止める係。

一番気を使ったのは独立性です。**各席には課題文だけを渡し、他席の出力も議長自身の見解も一切見せません。** 先に片方の意見を見せると、もう片方がそれに引きずられて、独立したチェックになりません。

**多数決は禁止**にしました。2席が同じことを言っても、それが正しい理由にはならないからです。実際、後の工程で**査読席の少数意見が採用されて、提案席の中核設計がひっくり返る**ことが起きています。

`ai-build-council` のほうは、設計・実装・レビューで**セッションを分けます。** 同じセッションに実装とレビューをやらせると、自分の書いたコードを自分で承認します。

そして2つのツールは、**コード上でつながっていません。** 稟議書が出た直後に実装が始まると、承認する隙がなくなるためです。「AIが決めてAIが作る」を一続きにしないのが狙いです。

`ai-build-council` のREADMEにはこう書いています。

> ai-councilの成果物をそのまま採用することは目的としない。

### 「分からないと書かせる」を形にする

各席の出力形式に、**必ず「不確実な点・前提」の欄**を入れています。相互レビューでは「未解決の論点（なければ「なし」と明記）」を返させます。**「なし」と書かせる**のが要点で、書かなければ「触れていない」のか「無い」のか区別できません。

実装側にも同じ仕掛けを入れました。工程の到達状況を記録する `state.json` には `not_done` という欄があります。

```json
"not_done": [
  "Stage 5: 固定diffの独立実装レビュー（2席）",
  "Stage 6: 指摘処理・Test Gate B"
],
"note": "Stage 0-4 まで完了。実機で動作確認した者はまだ居ない。"
```

実際、公開した拡張は**Stage 5 を飛ばしたまま**です。飛ばしたなら飛ばしたと書く。書かないと、次に読む人（未来の自分を含む）が「レビュー済みのコード」だと誤解します。

## 回してみた結果

| 項目 | 結果 |
|---|---|
| 会合の回数 | 3回 |
| 出た案の総数 | 55件（稼働キュー37＋候補プール18） |
| **ストア公開まで到達** | **5件** |

**案は余りました。** 3席に投げれば1回の会合で30案出ます。足りないということが起きません。

詰まったのはその先です。実装は済んでいるのに提出していない在庫が積み上がり、第3回の会合では**提案席と査読席が独立に「新規案をこれ以上積み増すな」という同じ結論**に達しました。案を出すために作ったツールが、案を出すのをやめろと言い出したわけです。

効いた対策は、**「完了」の定義を変えたこと**でした。

> 完了 ＝ Chromeウェブストアで公開完了。実装完了・提出準備完了は成功指標として**0点**で数える。

数えるのをやめた瞬間、在庫は成果ではなく負債として見えるようになります。

## 最初の方針は正しかったか

**部分的に正しく、そして自分でも予想していなかった形で裏付けられました。**

実装工程で、**自動テスト99件を通過したコードを実機のChromeに載せたら6件の不具合**が出ました。内訳がこうでした。

- **2件は要件そのものの誤り。** テストは要件を正しく反映していた
- 1件はモックが実機の挙動を持たない領域
- 1件はCSS（テスト対象外）
- 1件はそもそもテストが1件も存在しない層

つまり「テストが弱かった」という話ではありません。

> **自動テストは要件と実装の一致しか見ない。要件が間違っていれば、テストは間違いを固定する。**

これは職務経歴書の `＜要記入＞` と同じ構造です。**テストが全部グリーンなことと、正しいことは違う。** グリーンは「書いてあるとおりに動く」以上のことを保証しません。そして緑色の画面は、確認済みに見えます。

チェックを多重にする方針は間違っていませんでした。ただし**チェックの種類を増やさないと意味がない**、というのが実際に回して分かったことです。同じ観点のチェックを3回かけても、通る不具合は3回とも通ります。
