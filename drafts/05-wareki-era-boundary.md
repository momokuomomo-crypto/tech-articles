# 和暦の元号境界は「1日ずれる」だけでは済まない — 実装の落とし穴6つをJDKで全部検証した

この記事は、[和暦変換Chrome拡張](https://chromewebstore.google.com/detail/pcgbpaagcljfakbhmoiaoekmfbfdfpob)を作る過程で踏んだ落とし穴をまとめた技術編です。作った経緯は[リリース編](#)にあります。

和暦を扱うコードのバグは、たいてい「元号が切り替わる日」の周辺で起きます。しかも厄介なことに、その多くは**例外を投げずに、間違った値を返す**タイプのバグです。

この記事では、近代5元号（明治・大正・昭和・平成・令和）の境界にひそむ落とし穴を6つ挙げます。すべて OpenJDK 21 の `java.time.chrono.JapaneseDate` で実際に動かして確認した結果を載せています。

## 前提：近代5元号の境界

まず正しい境界を押さえます。

| 元号 | 開始 | 終了 |
|---|---|---|
| 明治 | 1868-10-23 | 1912-07-30 |
| 大正 | 1912-07-30 | 1926-12-25 |
| 昭和 | 1926-12-25 | 1989-01-07 |
| 平成 | 1989-01-08 | 2019-04-30 |
| 令和 | 2019-05-01 | — |

開始日と終了日が**同じ日で重なっている**箇所があることに注意してください。ここが落とし穴2につながります。

## 落とし穴1：昭和64年は7日間しかない

昭和天皇の崩御が 1989-01-07。翌日から平成です。つまり **昭和64年は1月1日から1月7日までの7日間しか存在しません**。

```
1989-01-01 -> Showa 64-01-01
1989-01-07 -> Showa 64-01-07
1989-01-08 -> Heisei 1-01-08
```

同様に**昭和元年も7日間**（1926-12-25〜12-31）、**大正元年は約5か月**、**令和元年は8か月**です。

「元号の1年目は12か月ある」という前提でテストデータを作ると、この7日間は永久にテストされません。年始の集計処理やバッチで `昭和64年1月` を月単位で扱うと、月末が1月31日ではなく1月7日である点を踏み外します。

## 落とし穴2：崩御による改元は「同じ日が2つの元号を持つ」

これはあまり知られていません。**改元のルールが時代によって違います。**

- **明治→大正（1912-07-30）と大正→昭和（1926-12-25）**：旧制度の「践祚即日改元」。天皇が崩御したその日のうちに改元されるため、**同じ1日が新旧2つの元号で表現されます**。1926-12-25 は「大正15年12月25日」でもあり「昭和元年12月25日」でもある。
- **昭和→平成（1989-01-07/08）**：元号法（1979年）下では政令の施行が翌日。だから重複しません。
- **平成→令和（2019-04-30/05-01）**：崩御ではなく譲位。事前に決まっていたので重複しません。

つまり**重複が起きるのは1912年と1926年の2日だけ**です。

そしてJDKは、この重複を片方に寄せています。

```
大正15年12月25日 -> REJECTED (year, month, and day not valid for Era)
昭和1年12月25日  -> 1926-12-25
```

歴史的には「大正15年12月25日」は正しい表記なのに、JDKはパースを拒否します。古い戸籍や登記簿から取り込んだデータにこの表記が入っていると、そこだけ落ちます。

## 落とし穴3：デフォルトのパーサは存在しない日付を黙って書き換える

**この記事で一番言いたいのはここです。**

「昭和64年1月8日」は存在しません（1月7日で昭和は終わり）。ではJDKに食わせるとどうなるか。`ResolverStyle` によって挙動が3通りに割れます。

```
STRICT   -> REJECTED (DateTimeParseException)
SMART    -> Heisei 1-01-08
LENIENT  -> Heisei 1-01-08
```

`DateTimeFormatter.ofPattern()` の**デフォルトは SMART**です。つまり何も指定しなければ、**存在しない日付が例外なしに平成元年1月8日へ黙って書き換えられます**。

入力バリデーションのつもりでパースしているなら、これは検知漏れです。手書き帳票のOCRや、利用者の手入力を受けるフォームで「昭和64年1月8日」が来たとき、エラーにならずに別の日付として通ってしまいます。

**和暦をパースするときは必ず `ResolverStyle.STRICT` を明示してください。**

```java
DateTimeFormatter f = DateTimeFormatter.ofPattern("GGGGy年M月d日")
    .withChronology(JapaneseChronology.INSTANCE)
    .withLocale(Locale.forLanguageTag("ja-JP-u-ca-japanese"))
    .withResolverStyle(ResolverStyle.STRICT);   // ← これを忘れない
```

## 落とし穴4：「元年」は自動では出力されない

正式な表記は「令和1年」ではなく「令和元年」です。しかしJDKは元年を知りません。

```
pattern GGGGy年M月d日   2019-05-01 -> 令和1年5月1日
pattern GGGGyy年M月d日  2019-05-01 -> 令和01年5月1日
```

出力側で「年が1なら元年に差し替える」処理を自分で書く必要があります。逆に入力側では「元年」と「1年」の両方を受け付ける必要があります。表示と保存で表記が揺れると、文字列比較での突き合わせが壊れます。

## 落とし穴5：明治5年12月3日〜30日は存在しない

明治政府は改暦（天保暦→グレゴリオ暦）を行い、**明治5年12月2日の翌日を明治6年1月1日**としました。つまり明治5年12月3日から12月30日までの28日間は、暦の上で存在しません。

この改暦のせいで、JDKは明治6年より前を扱えません。

```
1868-01-01 -> EXCEPTION: JapaneseDate before Meiji 6 is not supported
1872-12-02 -> EXCEPTION: JapaneseDate before Meiji 6 is not supported
1873-01-01 -> Meiji 6-01-01   ← ここが下限
```

`JapaneseChronology.INSTANCE.range(ChronoField.YEAR)` も `1873 - 999999999` を返します。明治元年〜5年を含む可能性のあるデータ（古い戸籍など）を扱うなら、標準ライブラリだけでは足りません。

## 落とし穴6：新元号は事前に分からない

令和の発表は 2019-04-01、施行は5月1日。**猶予は1か月**でした。次も同じとは限りません。

元号をenumやswitch文にハードコードしていると、改元のたびにコード修正と再デプロイが必要になります。少なくとも、次の元号が来たときに**コードではなく設定で対応できる**構造にしておくべきです。

JDKには将来元号を試すための仕組みがあります。システムプロパティ `jdk.calendar.japanese.supplemental.era` で仮の元号を追加できます。

```bash
java -Djdk.calendar.japanese.supplemental.era="name=Tester,abbr=T,since=1924992000000" App
```

`since` はエポックミリ秒（上の例は 2031-01-01 起点）。実際に動かすと：

```
# 指定なし
eras known: [Meiji, Taisho, Showa, Heisei, Reiwa]
2031-03-01 -> Reiwa 13-03-01

# 指定あり
eras known: [Meiji, Taisho, Showa, Heisei, Reiwa, Tester]
2031-03-01 -> Tester 1-03-01
```

**改元前に、改元後の挙動をCIで検証できます。** 令和のときに慌てた経験があるなら、次はこれを仕込んでおくと違います。

## 最低限入れておきたいテストケース

境界そのものと、その前後1日を必ず含めます。

| 日付 | 期待 |
|---|---|
| 1873-01-01 | 明治6年1月1日（ライブラリ下限） |
| 1912-07-29 / 07-30 | 明治45年 / 大正元年（同日重複あり） |
| 1926-12-24 / 12-25 | 大正15年 / 昭和元年（同日重複あり） |
| 1926-12-31 | 昭和元年12月31日（元年は7日間） |
| 1989-01-07 / 01-08 | 昭和64年 / 平成元年 |
| 2019-04-30 / 05-01 | 平成31年 / 令和元年 |
| 「昭和64年1月8日」 | **STRICTで例外**（SMARTだと平成元年に化ける） |
| 「令和元年5月1日」 | 元年表記のパース |
| 1872-12-15 | 存在しない日（改暦の空白） |

## まとめ

- 元号の1年目は12か月あるとは限らない。**昭和64年と昭和元年は7日間**
- **1912-07-30 と 1926-12-25 は、同じ日が2つの元号を持つ**。JDKは片方しか受け付けない
- **パースは `ResolverStyle.STRICT` を明示する**。デフォルトのSMARTは存在しない日付を黙って書き換える
- **「元年」は自前で処理する**。JDKは「1年」としか出さない
- **明治6年（1873-01-01）より前は標準ライブラリの範囲外**
- **次の改元は `jdk.calendar.japanese.supplemental.era` で先に試せる**

和暦のバグは、境界の1日を踏むまで表に出てきません。だからこそ境界日をテストに固定してしまうのが一番効きます。

---

本記事の挙動はすべて OpenJDK 21.0.10 で確認しました。他の言語・ランタイム（.NET の `JapaneseCalendar`、ICU、各種DBの和暦関数）は境界の扱いや対応範囲が異なる場合があるため、お使いの環境でも同じテストケースを流すことをおすすめします。
