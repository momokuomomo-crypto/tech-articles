# AIに役割を分けて会議させる仕組みを作って、Chrome拡張を1本公開するまで

AIを開発に使うとき、**1つのセッションに全部やらせるのをやめました。** 役割を分けて、複数のチェックを通す仕組みを作っています。

議論用と実装用の2つを作り、実際にその流れでChrome拡張を1本、Chromeウェブストアまで出しました。この記事はその全体像です。

## 作ったもの

| | 役割 | 記事 |
|---|---|---|
| [ai-council_v2](https://github.com/momokuomomo-crypto/ai-council_v2) | 何を作るかを決める（議論・意思決定） | [案出し編](@02) |
| [ai-build-council](https://github.com/momokuomomo-crypto/ai-build-council) | どう作るかを決めて実装する | [実装編](@03) |
| [chrome-ext-wareki-converter](https://github.com/momokuomomo-crypto/chrome-ext-wareki-converter) | 実際に作って公開したもの | [アプリ編](@04) |

どちらもClaude Codeのスキルです。使うのは **Claude Code**（サブスクリプション）と **Codex CLI**（ChatGPTプラン）だけで、APIの従量課金は使っていません。

```text

        ▼

        │

   Chromeウェブストア公開
```

## なぜ役割を分けるのか

1つのAIに「案を出して」と頼めば、質の高い案が返ってきます。ただし**その案に反論する人がいません。** 同じセッションに検算させても、同じ前提の上をもう一度通るだけです。

**別のセッション、できれば別のモデルに、前の出力を見せずに検討させる。** これをやると、1つでは出てこない指摘が出ます。

`ai-council` は3席に分けています。

| 席 | モデル | 役割 |
|---|---|---|
| **議長** | Claude Fable | 論点整理・統合・裁定 |
| **提案** | GPT（Codex CLI） | 実現案・技術選定・具体策 |
| **査読** | Claude（サブエージェント） | 前提・リスク・矛盾・欠落の指摘 |

対等な3社ではなく、**役割で非対称**にしているのが要点です。提案席は前に進める係、査読席は止める係、議長は決める係。

一番気を使ったのは独立性です。**各席には課題文だけを渡し、他席の出力も議長自身の見解も見せません。** 先に片方の意見を見せると、もう片方がそれに引きずられて、独立したチェックになりません。

そして**多数決は禁止**にしました。2席が同じことを言っても、それが正しい理由にはならないからです。目的適合性・制約充足・根拠の強さ・リスクの4観点で、どの主張をなぜ採ったかを議長が書き残します。

## 分けた効果が出た例

実装工程で、**査読席の指摘が提案席の中核設計をひっくり返しました。**

論点は「同梱の元号データの確認期限を超える日付をどう扱うか」。提案席の設計は「**変換を止める**」でした。正確さを優先した、筋の通った判断です。

査読席は反対し、根拠に**失敗の非対称性**を挙げました。

| | 誤変換のリスク | 停止のコスト |
|---|---|---|
| 発生条件 | 改元が**起きたとき**、改元日以降の日付のみ | 改元が**起きなくても**、期限以降のすべての日付 |
| 影響範囲 | 限定的 | 全面的 |

確認期限はビルド時に凍結される値なので、更新が止まれば時間の経過だけで「今日の日付が変換できない和暦変換拡張」ができあがります。議長は査読席を採りました。

**多数決にしていたら通らなかった判断です。** 役割を分けたことが、そのまま設計の質になりました。

さらに査読席は、**流用元の実コードまで読みに行って**こう指摘しています。設計書は「無警告で令和XX年を返す設計は採らない」と宣言しているのに、コピーしてくる予定のコードが `WAREKI_DISPLAY_HORIZON_YEARS = 100` で**2119年まで「令和101年」を無警告で返す**実装だった、と。設計書だけを読んでいては出ない種類の指摘です。

## 2つのツールをつなげない

`ai-council` と `ai-build-council` は、**コード上でつながっていません。** 連携はファイルを渡すだけです。

稟議書が出た直後に実装が始まってしまうと、人間が承認する隙がなくなるためです。「AIが決めてAIが作る」を一続きにしないのが狙いです。

実装側は議論側の結論を鵜呑みにもしません。`ai-build-council` のREADMEにはこう書いています。

> ai-councilの成果物をそのまま採用することは目的としない。

実装側は独自に設計し直します。ここでも同じ考え方で、**同じ結論に別ルートから到達するか**を見ています。

## 工程を定義しておく効果

`ai-build-council` は工程を Stage 0〜7 まで定義し、到達状況を `state.json` に記録します。

```json
"not_done": [
  "Stage 5: 固定diffの独立実装レビュー（2席）",
  "Stage 6: 指摘処理・Test Gate B"
],
"note": "Stage 0-4 まで完了。実機で動作確認した者はまだ居ない。"
```

公開した拡張は、実は**Stage 5 を飛ばしています。**

ここで効いているのは、**飛ばしたことが記録に残る**という点です。工程を定義していなければ「レビュー済みかどうか」自体が曖昧なまま残ります。定義してあるから、何が済んでいて何が済んでいないかを、後から読んで判断できます。

同じ考えを各席の出力形式にも入れました。相互レビューでは「未解決の論点（なければ**「なし」と明記**）」を返させています。書かせないと、触れていないのか無いのかが区別できません。

## 回してみた結果

| 項目 | 結果 |
|---|---|
| 会合の回数 | 3回 |
| 出た案の総数 | 55件（稼働キュー37＋候補プール18） |
| **ストア公開まで到達** | **5件** |

**案出しは、期待以上に回りました。** 3席に投げれば1回の会合で30案出ます。足りないということが起きません。

面白かったのはその先です。実装は済んでいるのに提出していない在庫が積み上がったとき、**提案席と査読席が独立に「新規案をこれ以上積み増すべきではない」という同じ結論**に達しました。案を出すために作ったツールが、案を出すのをやめようと言ってきたわけです。

独立した2席が同じ結論に達したので、これは採りました。効いた対策は**「完了」の定義を変えたこと**です。

> 完了 ＝ Chromeウェブストアで公開完了。実装完了・提出準備完了は成功指標として**0点**で数える。

数えるのをやめた瞬間、在庫は成果ではなく、片付けるべきものとして見えるようになりました。

## チェックは、種類を増やすと効く

実装工程で、**自動テスト99件を通過したコードを実機のChromeに載せたら6件の不具合**が見つかりました。内訳がはっきりしています。

- **2件は要件そのものの誤り。** テストは要件を正しく反映していた
- 1件はモックが実機の挙動を持たない領域
- 1件はCSS（テスト対象外）
- 1件はそもそもテストが1件も存在しない層

**テストが弱かったわけではありません。** 自動テストは要件と実装の一致を見るものなので、要件のほうが間違っていれば、正しく動いていることを確認し続けます。

だから**実機で触るという別種のチェック**が効きました。同じ観点のチェックを3回かけても、通るものは3回とも通ります。**チェックは回数ではなく種類を増やすと効く**、というのが実際に回して分かったことです。

6件はすべて修正し、回帰テストを追加しました。テストは99件から152件に増えています。
