# AIに案を出させ、AIに実装させ、Chromeウェブストアで公開するまで（全体像）

Chrome拡張のアイデア出しから実装、ストア公開までを、2つのClaude Codeスキルで回した記録です。この記事は全体像で、各工程の詳細は個別記事に分けています。

結果を先に書きます。

- **案を55件出した**（稼働キュー37件＋候補プール18件）
- **Chromeウェブストアで公開できたのは5本**
- 5本目が「和暦変換（改元日対応）」（2026-08-05公開）

**案は余るほど出ます。詰まるのはその先です。** この記事で一番伝えたいのはそこです。

## シリーズ構成

1. **本記事** — 全体像
2. [案出し編] AI3席会合で55案出したら、在庫が積み上がった話（`ai-council_v2`）
3. [実装編] AIに実装させるゲート設計と、自動テスト99件をすり抜けた6件のバグ（`ai-build-council`）
4. [リリース編] 和暦変換Chrome拡張を公開するまで（`chrome-ext-wareki-converter`）
5. [技術編] 和暦の元号境界は「1日ずれる」だけでは済まない

## 全体の流れ

```text
 テーマ「Chrome拡張で何を作るか」
        │
        ▼
┌───────────────────────┐
│ ai-council_v2         │  議長Fable・提案GPT・査読Claude の3席会合
│ 「何を作るか」を決める  │  独立意見 → 相互レビュー → 統合・裁定
└───────────────────────┘
        │  稟議書（裁定つき）
        ▼
    ★ 人間が承認 ★        ← ここは自動化しない
        │
        ▼
┌───────────────────────┐
│ ai-build-council      │  Stage 0〜7、ゲートつき
│ 「どう作るか」と実装    │  設計 → 査読 → 実装 → テスト → レビュー
└───────────────────────┘
        │  動くコード
        ▼
    ★ 人間が実機確認 ★    ← ここも自動化しない
        │
        ▼

```

## 2つのツールを分けた理由

`ai-council` は議論と意思決定、`ai-build-council` は設計と実装。役割で分かれています。

重要なのは、**この2つがコード上でつながっていないこと**です。連携はファイルを渡すだけで、片方の出力がそのままもう片方の入力に流れ込むことはありません。

なぜかというと、**間に人間の承認を挟むためです。** 稟議書が出た直後に実装が始まってしまうと、承認する隙がなくなります。「AIが決めてAIが作る」を一続きにしないことが、この構成の狙いです。

`ai-build-council` の README にはこう書かれています。

> ai-councilの成果物をそのまま採用することは目的としない。

実装側は、議論側の結論を鵜呑みにせず独自に設計し直します。

## 数字で見る結果

| 項目 | 件数 |
|---|---|
| 会合の回数 | 3回 |
| 出た案の総数 | 55件（稼働キュー37＋候補プール18） |
| 実装まで到達 | 十数件 |
| **ストア公開まで到達** | **5件** |

案出しは驚くほど簡単です。3席のAIに投げれば、1回の会合で30案（提案席15＋査読席15）が出ます。

問題はその先で、**実装は済んでいるのに提出していない在庫が積み上がりました。** 第3回の会合では、提案席と査読席が独立に「新規案をこれ以上キューに積むべきではない」という同じ結論に達しています。案を出すツールが「案を出すのをやめろ」と言い出した形です。

対応として、こういうルールを入れました。

- **完了の定義＝ストア公開完了。** 実装完了・提出準備完了は成果として0点で数える
- **WIP上限**：未提出在庫5件以下、新規実装は同時1件まで、提出は週2本まで
- **案の3層管理**：稼働キュー／候補プール／裁定済みアーカイブ

「実装が終わった」を成果に数えるのをやめたのが効きました。数えるのをやめた瞬間、在庫は成果ではなく負債として見えるようになります。

## 実装工程で分かったこと

詳細は実装編に書きますが、ここだけは全体像として先に出しておきます。

**自動テスト99件を通過したコードを実機のChromeに載せたら、6件の不具合が出ました。**

しかもその内訳が示唆的でした。

- 2件は**要件そのものの誤り**。テストは要件を正しく反映していた
- 1件はモックが実機の挙動を持たない領域（通知IDの使い回し）
- 1件はCSS（テストの対象外）
- 1件はそもそもテストが1件も存在しない層

つまり「テストが弱かった」という話ではありません。

> 自動テストは要件と実装の一致しか見ない。要件が間違っていれば、テストは間違いを固定する。

AIに実装させると、テストも一緒に書いてくれます。ただしそのテストは**要件を写したもの**なので、要件が間違っていれば、間違いごと固定されます。ここは人間が実機を触るしかありませんでした。

## 正直に書いておくこと

この工程は完走していません。`ai-build-council` の Stage 5（実装者以外の2席が、固定したdiffを独立にレビューする工程）は**未実施のまま公開しています。**

姉妹拡張では、この Stage 5 で blocker 1件・major 6件が見つかっています。いずれも自動テスト139件を通過した状態ですり抜けていたものでした。うち1件は「先頭ラベル除去が誤った日付を無警告で受理する」という、**症状として表に出ない**タイプの欠陥です。

実機スモークテストは Stage 5 の代わりになりません。実機で分かるのは触った経路の症状だけで、Stage 5 が探すのは触っていない経路の設計上の欠陥だからです。
