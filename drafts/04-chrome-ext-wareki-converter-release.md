## 何を作ったか

西暦と和暦を日付単位で相互変換するChrome拡張です。

```
入力：1989/1/8

  平成元年1月8日
  1989年1月8日
  ※ 1989年は1月7日までが昭和64年、1月8日からが平成元年
```

## 既存の和暦変換拡張との違い

和暦変換の拡張はすでにあります。差別化点は1つに絞りました。

**改元のあった年は、境界日を注記で示す。**

同じ1989年でも、1月7日までは昭和64年、1月8日からは平成元年です。多くの変換ツールは「1989年 → 平成元年」と答えて終わりますが、これは1月1日〜7日について**間違い**です。

この境界を能動的に教えるのが、この拡張の存在理由です。

### 存在しない和暦は作らない

`昭和64年1月8日` は存在しません。昭和は1月7日で終わっているからです。

この拡張は、そういう入力に対して**存在しない和暦を作りません。** 期間外であることを示したうえで「この日付は 平成元年1月8日 です」と正解を併記します。

一見あたりまえですが、[技術編](#)に書いたとおり、Javaの標準ライブラリですら**デフォルト設定では `昭和64年1月8日` を例外なしに `平成元年1月8日` へ黙って書き換えます。** 黙って直すのと、間違いを指摘したうえで正解を出すのは別のことです。

### 年だけでも変換できる

`1901` と入れれば明治34年。改元のあった年は、両方を境界つきで並べます。

### 表記ゆれを吸収する

実際の入力は綺麗ではありません。以下をすべて受理します。

```
1989/1/8        19890108        1989年1月8日
平成元年1月8日   H1.1.8          H1年1月8日
H元/1/8         西暦1989年1月8日  １９８９年１月８日（全角）
生年月日：1989年1月8日            1989年1月8日（日）
```

`生年月日：` のような先頭ラベル付きと、`（日）` のような曜日付きに対応しているのは、**実際にコピペされる文字列がそういう形をしているから**です。

## 権限を3つに絞った

```
contextMenus, storage, notifications
```

これだけです。**ページの内容を読み取る権限（`host_permissions`・`activeTab`・`scripting`）は要求せず、外部通信も一切行いません。**

権限を絞ったのは審査対策でもあります。拡張の権限が増えるほど、なぜ必要かの説明が求められ、審査が長引きます。

ビルド成果物の検査を自動化して、**外部URL参照・`eval`・`new Function`・想定外の権限・`host_permissions` の混入を機械的に弾く**ようにしました（`npm run verify`）。うっかり増えたら、ビルドが落ちます。

## 制限事項を先に書く

ストア掲載文にも、READMEにも、制限を明記しました。

- **1873年1月1日（明治6年1月1日）以降**のみ対応。明治5年以前は旧暦のため、元号年から西暦への機械換算が成立しない
- 同梱の元号データには確認期限がある。それを超える日付も変換するが、**以降に改元があった場合は正しい和暦が異なる旨の注記**が付く
- 右クリックの結果はChromeの通知に表示する。OS側で通知が抑制されている場合（Windowsの集中モード等）は検知できない。その場合はポップアップに結果が残る

2つ目は[実装編](#)に書いた、査読席が中核設計をひっくり返した論点そのものです。「確認期限を超えたら変換を止める」設計を「変換は続けて注記を付ける」に変えました。止めると、更新が止まった瞬間から**今日の日付が変換できない和暦変換拡張**になるためです。

## ストア提出で気をつけたこと

掲載情報の下書きに、冒頭からこう書いています。

> **この拡張は外部通信を一切行わず、データを一切収集しない**ため、どの欄も「収集しない」で一貫させる。事実と異なる申告をすると審査で差し戻される。

データ収集の申告欄は、実装と食い違うと差し戻されます。**先に「収集しない」で全部埋まる設計にしておく**のが結局いちばん速い、という判断でした。

概要文は132文字以内の制限に対して71文字に収めています。

> 西暦と和暦を日付単位で相互変換します。改元のあった年は境界日を注記で示し、昭和64年1月8日のような存在しない和暦は作りません。外部送信なし。

差別化点（境界日を示す）と、具体例（昭和64年1月8日）と、安心材料（外部送信なし）を1文ずつ入れました。

## 提出ペースの制約

[案出し編](#)に書いたWIP上限のうち、ストア提出に効くのはこれです。

- ストア提出準備中：同時**2件**まで
- 同時に審査中：**3件**まで
- 提出ペース：**週2本**まで

週2本の根拠は工数ではなく、**スパム／重複コンテンツ判定のリスクと審査キュー**です。似た拡張を短期間に大量投入すると審査で不利になります。

実際、機能が近い2本（サイト別ズームと拡大リーダー）には「**3週間以上空けて提出する**」という条件が付きました。加えて、説明文・スクリーンショット・拡張名で**解く問題を分ける**こと。同じ問題を解く2本に見えると重複と判定されます。
