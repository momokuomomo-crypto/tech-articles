# AI3席会合で55案出したら、在庫が積み上がった話

[前回](#)の全体像に続いて、案出し工程の詳細です。使ったのは自作のClaude Codeスキル [ai-council_v2](https://github.com/momokuomomo-crypto/ai-council_v2)。

結論から書くと、**案出しはAIで解決しました。解決しなかったのは、出た案をさばくほうです。**

## 3席で会合させる

1つのAIに「Chrome拡張のアイデアを出して」と頼むと、それなりのものが返ってきます。ただし**反論する人がいません。** 出てきた案の弱点は、自分で探すことになります。

そこで3席に分けました。

| 席 | モデル | 役割 |
|---|---|---|
| **議長** | Claude Fable | 論点整理・統合・裁定 |
| **提案** | GPT（Codex CLI） | 実現案・技術選定・具体策 |
| **査読** | Claude（サブエージェント） | 前提の誤り・リスク・矛盾・欠落の指摘 |

対等な3社ではなく、**役割で非対称にしている**のが要点です。提案席は前に進める係、査読席は止める係、議長は決める係。同じ質問を3つのAIに投げて多数決を取る構成ではありません。

## 処理の流れ

```text
テーマ + 参考情報
      │
      ▼
Stage 0: 論点整理（議長）
      │
 ┌────┴────┐
 ▼         ▼
提案(GPT)  査読(Claude)   Stage 1: 独立意見（互いの出力は見せない）
 └────┬────┘
      ▼
Stage 2: 相互レビュー（既定1ラウンド）
      │
      ▼
Stage 3: 統合・裁定（議長）
  承認 / 条件付き承認 / 差し戻し / 却下
      │
      ▼
稟議書 + 議事録 → 人がレビュー・採否判断
```

### Stage 1で独立性を守る

ここが一番気を使った部分です。スキルにはこう書いています。

> **独立性の担保が最重要**：各席には課題文（テーマ＋参考情報＋Stage 0の論点整理）だけを渡し、他席の出力・議長自身の見解・誘導を一切含めない。2席は並列で実行する。

先に片方の意見を見せると、もう片方がそれに引きずられます。議長が自分の見解を混ぜても同じです。**独立した意見が2つ揃わないと、相互レビューが成立しません。**

### 裁定は多数決にしない

Stage 3の裁定は4種類です。

- **承認** — そのまま採用してよい
- **条件付き承認** — 列挙した条件（各条件に理由をつける）を満たせば採用可
- **差し戻し** — 修正指示を明記してStage 1からやり直す（自動での差し戻しは1回まで）
- **却下** — 理由と、可能なら代替案を示す

スキルには「**多数決は禁止**」と明記しています。2席が同じことを言っても、それが正しい理由にはならないからです。目的適合性・制約充足・根拠の強さ・リスクの4観点で、どの主張をなぜ採ったかを議長が書き残します。

実際、後の工程では**査読席の少数意見が採用されて、提案席の中核設計がひっくり返る**ことが起きました（実装編に書きます）。多数決にしていたら潰れていた判断です。

## 実際に何が出たか

Chrome拡張のアイデアというテーマで、会合を3回行いました。

3回目では、提案席と査読席がそれぞれ独立に15案ずつ、**合計30案**を出しています。最終的に管理下にある案は**55件**です。

| 層 | 件数 | 位置づけ |
|---|---|---|
| 稼働キュー | 37件 | 実装・提出の対象として現に動かす案 |
| 候補プール | 18件 | 競合調査前の案。採択数には数えない |

**案は余ります。** これが最初の発見でした。3席に投げれば1回で30案出ます。足りないということが起きません。

## そして詰まった

問題はここからです。第3回の会合で、提案席と査読席が**独立に同じ結論**に達しました。

> 新規案を実装キューへ積み増すべきではない

理由は、**実装は済んでいるのにストアへ提出していない在庫が15本あり、公開できているのは4本だけ**という状態だったからです。ここに案を足せば、在庫が増えるだけになります。

案を出すために作ったツールが、「案を出すのをやめろ」と言い出したわけです。

### 効いた対策：「完了」の定義を変えた

一番効いたのはこれでした。

> **完了 ＝ Chromeウェブストアで公開完了。** 実装完了・提出準備完了は成功指標として0点で数える。

それまで「実装が終わった」を進捗として数えていました。数えるのをやめた瞬間、**在庫は成果ではなく負債として見える**ようになります。

工程状態はこう定義し直しました。

```
未着手 → 設計中 → 実装中 → 実装済み（監査待ち） → 開発完了（提出可能）
      → 出荷完了（提出済み） → 審査中 → 公開完了
```

中間状態を残したのは、**どこで滞留したかを測るため**です。実際、滞留は「実装済み（監査待ち）」に集中していました。

### WIP上限を入れた

目標ではなく制約として設定しています。

- 未提出在庫（実装済み〜出荷完了）：**5件以下**
- ストア提出準備中：同時**2件**まで
- 新規実装中：同時**1件**まで
- 同時に審査中：**3件**まで
- 提出ペース：**週2本**まで

最後の「週2本まで」の根拠は工数ではありません。**スパム／重複コンテンツ判定のリスクと審査キュー**です。似た拡張を短期間に大量投入すると、審査で不利になります。

### 実装時間の見積りを選別軸から外した

第3回で最も影響が大きかった裁定がこれでした。「実装が早く終わりそうな案から着手する」という基準をやめています。

実装完了が0点なら、**実装が速いことに価値はありません。** ボトルネックは実装ではなく提出だったので、実装時間で並べ替えても公開本数は増えません。

## 案の選び方

新規実装の1件目を選ぶとき、**即決していません。** 3案に絞ったうえで、こういうゲートを通しています。

> 3候補について競合調査とストア掲載文を作り、**人間が「自分ならインストールするか」を判定**してから1件だけ着手する

AIに「どれが良いか」を選ばせていません。競合調査とストア掲載文まで作らせて、**最後の判定だけ人間がやる**構成です。掲載文を先に書くと、その拡張が何の問題を解くのか、既存のものと何が違うのかが、実装前にはっきりします。

このゲートを通って選ばれたのが「和暦変換（改元日対応）」でした。

## 出力の作り方で気をつけたこと

スキルにこう書いています。

> **重要：ファイルは必ず自己完結させる。**「詳細はチャット出力を参照」のような、チャット側にしか実体がない内容への参照だけで済ませてはならない。

AIに長い一覧を出させると、ファイルには「上記のとおり30案を検討した」とだけ書いて、中身をチャットに置き去りにすることがあります。**チャットは残りません。** 大量の項目であっても実体をファイルに書き切らせる必要がありました。

もう1つ、成果物は非公開リポジトリに分けています。会合のテーマには個人的な相談も入るため、ツール本体（公開）と結果を分離しました。pushの前には必ず確認を挟みます。

## まとめ

- **3席に分けると反論が出る。** 提案・査読・議長を役割で非対称にする
- **独立性が命。** Stage 1では他席の出力も議長の見解も渡さない
- **多数決は禁止。** 少数意見が正しいことがある
- **案は余る。** 詰まるのは案出しではなく、その先の提出工程
- **「完了」の定義を変えると在庫が見える。** 実装完了は0点で数える
- **最後の採否は人間が判定する。** 「自分ならインストールするか」
