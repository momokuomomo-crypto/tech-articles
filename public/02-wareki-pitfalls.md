業務システムで和暦を扱っていると、バグはたいてい元号が切り替わる日の周辺で出ます。しかもその多くは、例外を投げずに誤った値を返します。落ちてくれれば気づけますが、静かに間違った日付が保存されます。

この記事では、近代5元号の境界にある罠を6つ挙げます。すべて OpenJDK 21 の `java.time.chrono.JapaneseDate` で実際に動かして確認した結果です。

## 前提となる近代5元号の境界

| 元号 | 開始 | 終了 |
|---|---|---|
| 明治 | 1868-10-23 | 1912-07-30 |
| 大正 | 1912-07-30 | 1926-12-25 |
| 昭和 | 1926-12-25 | 1989-01-07 |
| 平成 | 1989-01-08 | 2019-04-30 |
| 令和 | 2019-05-01 | — |

開始日と終了日が同じ日で重なっている箇所があります。これが2つ目の罠です。

## 罠1　昭和64年は7日間しかない

昭和天皇の崩御が1989-01-07で、翌日から平成です。昭和64年は1月1日から1月7日までの7日間しか存在しません。

```
1989-01-01 -> Showa 64-01-01
1989-01-07 -> Showa 64-01-07
1989-01-08 -> Heisei 1-01-08
```

元年が短いのは昭和だけではありません。

- 昭和元年：7日間（1926-12-25から12-31）
- 大正元年：約5か月
- 令和元年：8か月

元号の1年目は12か月あるという前提でテストデータを作ると、この7日間は永久にテストされません。年始のバッチや月次集計で昭和64年1月を月単位で扱うと、月末が1月31日ではなく1月7日である点を踏み外します。

## 罠2　崩御による改元は、同じ日が2つの元号を持つ

改元のルールが時代によって違います。

- 明治から大正（1912-07-30）と大正から昭和（1926-12-25）は、旧制度の践祚即日改元による。崩御したその日のうちに改元されるため、同じ1日が新旧2つの元号で表現される。1926-12-25 は大正15年12月25日でもあり、昭和元年12月25日でもある
- 昭和から平成（1989-01-07から08）は、元号法のもとで政令の施行が翌日になるため重複しない
- 平成から令和（2019-04-30から05-01）は崩御ではなく譲位のため重複しない

重複が起きるのは1912年と1926年の2日だけです。

JDKはこの重複を片方に寄せています。

```
大正15年12月25日 -> REJECTED (year, month, and day not valid for Era)
昭和1年12月25日  -> 1926-12-25
```

歴史的には大正15年12月25日が正しい表記ですが、JDKはパースを拒否します。**古い戸籍や登記簿から取り込んだデータにこの表記が混ざっていると、そのレコードだけ落ちます。** 移行案件で全件変換をかけたときに出る種類の障害です。

## 罠3　デフォルトのパーサは存在しない日付を黙って書き換える

この記事でもっとも伝えたい罠です。

存在しない昭和64年1月8日をJDKに渡すと、`ResolverStyle` によって挙動が3通りに割れます。

```
STRICT   -> REJECTED (DateTimeParseException)
SMART    -> Heisei 1-01-08
LENIENT  -> Heisei 1-01-08
```

`DateTimeFormatter.ofPattern()` のデフォルトは SMART です。何も指定しなければ、**存在しない日付が例外なしに平成元年1月8日へ書き換えられます。**

入力バリデーションのつもりでパースしているなら、これは検知漏れです。OCRで読み取った手書き帳票や、利用者の手入力を受けるフォームを考えてください。昭和64年1月8日が来ても、エラーにならずに別の日付として通ります。

和暦をパースするときは `ResolverStyle.STRICT` を明示するほうが安全です。

```java
DateTimeFormatter f = DateTimeFormatter.ofPattern("GGGGy年M月d日")
    .withChronology(JapaneseChronology.INSTANCE)
    .withLocale(Locale.forLanguageTag("ja-JP-u-ca-japanese"))
    .withResolverStyle(ResolverStyle.STRICT);
```

既存システムを引き継いだなら、`ofPattern` を検索して `withResolverStyle` の指定漏れを確認する価値があります。

## 罠4　元年は自動では出力されない

正式な表記は令和1年ではなく令和元年ですが、JDKは元年を知りません。

```
pattern GGGGy年M月d日   2019-05-01 -> 令和1年5月1日
pattern GGGGyy年M月d日  2019-05-01 -> 令和01年5月1日
```

出力側で、年が1なら元年に差し替える処理を自分で書く必要があります。入力側では元年と1年の両方を受け付ける必要があります。**帳票の表示とDBの保存で表記が揺れると、文字列比較での突き合わせが壊れます。** 別システムとの連携でキーに使っている場合は特に効きます。

## 罠5　明治5年12月3日から30日は存在しない

明治政府は改暦（天保暦からグレゴリオ暦へ）を行い、明治5年12月2日の翌日を明治6年1月1日としました。明治5年12月3日から12月30日までの28日間は、暦の上で存在しません。

この改暦のため、JDKは明治6年より前を扱えません。

```
1868-01-01 -> EXCEPTION: JapaneseDate before Meiji 6 is not supported
1872-12-02 -> EXCEPTION: JapaneseDate before Meiji 6 is not supported
1873-01-01 -> Meiji 6-01-01
```

`JapaneseChronology.INSTANCE.range(ChronoField.YEAR)` も `1873 - 999999999` を返します。

明治元年から5年を含みうるデータ（古い戸籍など）を扱うなら、標準ライブラリだけでは足りません。明治5年以前は旧暦のため、元号年から西暦への機械換算がそもそも成立しないためです。

## 罠6　新元号は事前に分からない

令和の発表は2019-04-01、施行は5月1日でした。猶予は1か月です。次も同じとは限りません。

元号をenumやswitch文にハードコードしていると、改元のたびにコード修正と再デプロイが必要になります。少なくとも、次の元号が来たときに**コードではなく設定で対応できる**構造にしておくほうが安全です。

JDKには将来元号を試す仕組みがあります。システムプロパティ `jdk.calendar.japanese.supplemental.era` で仮の元号を追加できます。

```bash
java -Djdk.calendar.japanese.supplemental.era="name=Tester,abbr=T,since=1924992000000" App
```

`since` はエポックミリ秒で、上の例は2031-01-01起点です。実際に動かすと次のようになります。

```
# 指定なし
eras known: [Meiji, Taisho, Showa, Heisei, Reiwa]
2031-03-01 -> Reiwa 13-03-01

# 指定あり
eras known: [Meiji, Taisho, Showa, Heisei, Reiwa, Tester]
2031-03-01 -> Tester 1-03-01
```

**改元前に、改元後の挙動をCIで検証できます。** 令和のときに慌てた経験があるなら、次はこれを仕込んでおくと動きが変わります。

## 最低限入れておきたいテストケース

境界そのものと、その前後1日を必ず含めます。

| 日付 | 期待 |
|---|---|
| 1873-01-01 | 明治6年1月1日（ライブラリ下限） |
| 1912-07-29 / 07-30 | 明治45年 / 大正元年（同日重複あり） |
| 1926-12-24 / 12-25 | 大正15年 / 昭和元年（同日重複あり） |
| 1926-12-31 | 昭和元年12月31日（元年は7日間） |
| 1989-01-07 / 01-08 | 昭和64年 / 平成元年 |
| 2019-04-30 / 05-01 | 平成31年 / 令和元年 |
| 「昭和64年1月8日」 | STRICTで例外。SMARTだと平成元年に化ける |
| 「令和元年5月1日」 | 元年表記のパース |
| 1872-12-15 | 存在しない日（改暦の空白） |

## 境界日を手元で確かめる

テストケースを書くときも、実装を突き合わせるときも、**その日が何年何月何日なのかを毎回引く**ことになります。1989年が昭和64年なのか平成元年なのかは、日付まで見ないと決まりません。

これを右クリックで確認できるようにChrome拡張を作りました。改元のあった年は境界日を注記で示し、存在しない和暦は作りません。

```
入力：1989/1/8

  平成元年1月8日
  1989年1月8日
  ※ 1989年は1月7日までが昭和64年、1月8日からが平成元年
```

存在しない和暦を入力した場合は、期間外であることを示します。そのうえで、その日付は平成元年1月8日であると正解を併記します。罠3で見たとおり、黙って書き換えないことを方針にしています。

表記ゆれも受理します。仕様書や既存データからそのままコピーして貼れます。

```
1989/1/8        19890108        1989年1月8日
平成元年1月8日   H1.1.8          H1年1月8日
H元/1/8         西暦1989年1月8日  １９８９年１月８日（全角）
生年月日：1989年1月8日            1989年1月8日（日）
```

権限は `contextMenus`・`storage`・`notifications` の3つだけです。ページの内容を読み取る権限（`host_permissions`・`activeTab`・`scripting`）は要求せず、外部通信も行いません。業務端末に入れる際の説明が要らない構成にしてあります。

## まとめ

- 元号の1年目は12か月あるとは限らない。昭和64年と昭和元年は7日間
- 1912-07-30 と 1926-12-25 は、同じ日が2つの元号を持つ。JDKは片方しか受け付けない
- パースは `ResolverStyle.STRICT` を明示する。デフォルトのSMARTは存在しない日付を黙って書き換える
- 元年は自前で処理する。JDKは1年としか出さない
- 明治6年（1873-01-01）より前は標準ライブラリの範囲外
- 次の改元は `jdk.calendar.japanese.supplemental.era` で先に試せる

和暦のバグは、境界の1日を踏むまで表に出てきません。境界日をテストに固定してしまうのがもっとも効きます。

---

本記事の挙動はすべて OpenJDK 21.0.10 で確認しました。他の言語・ランタイムは、境界の扱いや対応範囲が異なる場合があります（.NET の `JapaneseCalendar`、ICU、各種DBの和暦関数など）。お使いの環境でも同じテストケースを流すことをおすすめします。
