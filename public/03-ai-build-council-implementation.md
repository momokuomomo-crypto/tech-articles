Chrome拡張を1本、工程ごとにゲートを置いた手順でAIに実装させました。使ったのは自作のClaude Codeスキル [ai-build-council](https://github.com/momokuomomo-crypto/ai-build-council) です。作ったのは西暦と和暦を相互変換する拡張で、以下では単に拡張と呼びます。

この記事の要点はひとつです。

> 自動テストは要件と実装の一致しか見ない。要件が間違っていれば、テストは間違いを固定する。

自動テスト99件が通った状態で実機のChromeに載せたところ、6件の不具合が出ました。その内訳が、AIに実装させるときの限界を示していたので、そこを中心に書きます。

## ワークフロー

```text
Stage 0: Intake・隔離・予算設定
Stage 1: 独立設計（Codex、新規セッション）
Stage 2: 設計査読・凍結（Claude査読、上限2ラウンド）
Stage 3: 実装（議長本体のみ、直接ファイル編集）
Stage 4: Test Gate A（実行結果で検証、上限5回）
Stage 5: 固定diffの独立実装レビュー（Codex 別新規セッション＋Claude査読）
Stage 6: 指摘処理（Fixed/WontFix/Disputed）・Test Gate B
Stage 7: 成果確定・commit・push・記録（事前承認ゲート、既定OFF）
```

設計と実装でセッションを分けています。Stage 1の設計はCodexの新規セッション、Stage 5のレビューはさらに別の新規セッションです。同じセッションに実装とレビューをやらせると、自分の書いたコードを自分で承認することになります。

## 安全側の既定値

- pushとGitHubのissue・PR作成は既定でオフ。事前に明示許可した場合のみ実行する
- テストは必ず実行結果で検証する。自己申告に頼らない
- レビュー指摘のうち blocker と major は、議長単独では対応不要を確定できない。人間の承認が必須
- `git add .` は使わず、対象ファイルを明示指定する

テストが通りましたというAIの報告を信じない、というのが Test Gate の趣旨です。実際にコマンドを走らせ、その出力で判定します。

`git add .` を禁止したのは、意図しないファイルが混入するためです。

## Stage 2で中核設計がひっくり返った

査読席は blocker 2件・major 5件・minor 10件を検出しました。さらに、Stage 1の中核判断をひとつ覆しています。

### 元号データの確認期限を超える日付をどうするか

この拡張は元号のデータを同梱しており、そのデータには「ここまでは正しいと確認した」という期限があります。改元があれば正しい和暦が変わるためです。期限を超える日付が入力されたとき、どう応答するかが論点になりました。

Stage 1の提案席は、最新元号を機械的に延長せず変換を止める設計を出しました。正確さを優先した判断です。

査読席はこれに反対し、根拠として**失敗の非対称性**を挙げました。

| | 誤変換のリスク | 停止のコスト |
|---|---|---|
| 発生条件 | 改元が起きたとき、改元日以降の日付のみ | 改元が起きなくても、期限以降のすべての日付 |
| 影響範囲 | 限定的 | 全面的 |

止めるほうが安全に見えます。しかし確認期限はビルド時に凍結される値です。したがって更新が止まれば、時間が経つだけで、今日の日付が変換できない和暦変換拡張ができあがります。

決め手はもうひとつありました。この拡張は全体を通して「事実は主表示、不確かさは注記」という形式で統一されています。確認期限だけが停止という強い扱いを取る整合的な理由がありません。

議長は査読席の主張を採り、変換は続行して警告注記を付す形に変更しました。

### 設計書だけ読んでいては出ない指摘

査読席は流用元の実コードまで読みに行きました。そして、`era.ts` の `WAREKI_DISPLAY_HORIZON_YEARS = 100` が2119年まで令和101年を無警告で返すと指摘しています。

設計書には、無警告で令和XX年を返す設計は採らないと明記されていました。ところが、コピーしてくる予定のコードがまさにそれを実装していたわけです。

しかも設計書には、移植直後に差分ゼロを確認するとも書いてありました。差分ゼロを達成した瞬間に設計違反が成立する、という自己矛盾です。

受入手順を、差分ゼロの確認から、差分を全件列挙して各差分に意図の根拠を添える形へ変更しました。

AIに設計させると、設計書自体は整合的に書けます。ただし設計書と流用元コードの整合までは見ていません。読みに行かせないかぎり出ない指摘です。

## Test Gate A の結果

| 項目 | 結果 |
|---|---|
| `npm run typecheck` | 通過 |
| `npm test` | 99件通過 |
| `npm run verify`（build から dist 検査） | 通過 |

試行2回（上限5回）で通過しました。

dist 検査は、外部URL参照・`eval`・`new Function`・想定外の権限・`host_permissions` の混入を機械的に弾きます。拡張機能は権限が増えると審査で不利になるので、ビルド成果物の側で機械チェックしています。

## そして実機で6件出た

`chrome://extensions` はブラウザ自動化ツールから遮断されており、拡張の実インストールを自動化できません。そのため人手で実施しました。

自動テスト99件を通過した状態で実機に載せた結果です。

| 症状 | なぜ自動テストで捕まらなかったか |
|---|---|
| 右クリックの通知が2回目以降表示されない | 通知IDを固定して使い回す実装。モックは `create` の呼び出しを記録するだけで、実機の通知センターが同一IDをどう扱うかを再現しない。モックは成功を返し続ける |
| `1901` など年のみの入力が一律で拒否される | 仕様どおりに動いていた。要件が年のみは受理しないと決めており、テストはそれを忠実に固定していた |
| コピーボタンが1回押すと二度と押せない | `navigator.clipboard.writeText` の同期例外が `.finally()` を迂回する経路。そもそもポップアップのテストが1件も無かった |
| 「もしかして」提案の改行が潰れる | 文言の生成は単体テストで固定していたが、CSSの `white-space` はDOMの見え方の話でテスト対象外 |
| `昭和100年` が「読み取れません」になる | 元号年を2桁に絞った正規表現。`昭和65年` は期間外と答えるのに `昭和100年` は形式エラー、という食い違いが、入力例を個別に並べたテストでは見えない |
| 区切りなし8桁（`19890108`）を受理しない | 要件が受理しない側に列挙していた。要件の写しでは検出できない |

### 内訳を分類する

- 2件は要件そのものの誤り。テストは要件を正しく反映していた
- 1件はモックが実機の振る舞いを持たない領域（通知IDの使い回し）
- 1件はCSSで、テストの対象外
- 1件はテストが1件も存在しない層（ポップアップ）

要件が間違っている2件は、テストを増やしても見つかりません。テストは要件の写しだからです。AIに実装させるとテストも一緒に書いてくれますが、そのテストは要件を固定するだけで、要件を疑いません。

6件はすべて修正し、それぞれ回帰テストを追加しました。テストは99件から152件に増えています。増分の中心は、実機で見つかった6件の回帰テストと、それまで存在しなかったポップアップの結合テストです。

## 既知の不具合パターン集

同じ種類の不具合を繰り返したため、パターン集をリポジトリに置いて毎回チェックさせるようにしました。現在12件あります。

1. 時刻・日時のハードコード（テストのタイムボム）
2. schemaVersion不整合時の無警告な空状態coercion
3. fire-and-forgetイベントリスナーの `.catch()` 欠如
4. 貪欲な正規表現マッチと末尾除去だけを前提にした抽出ロジック
5. 部分文字列一致による機密情報判定がURL構造を無視する
6. 列挙可能なコレクション（Map/Set）の掃除漏れ（メモリリーク）
7. Chromeのmatch patternがポート番号を表現できないことの波及
8. ビルド成果物のコンテンツハッシュ変化をreconcileが検知しない
9. 連打・二重クリックへの防御が無い
10. 同一固定位置に複数の一時UI要素が生成され重なる
11. 通知後・完了後の記録が永続的に残り続ける
12. `chrome.contextMenus.OnClickData.selectionText` が段落区切りの改行を保持しない

冒頭にこう書いてあります。

> すべて、chrome API mockの単体テストが全件パスした状態で実際に発見された不具合であり、「テストが通っている」ことは「このクラスの不具合が無い」ことを保証しない。

AIは同じ種類のミスを繰り返します。一度踏んだ地雷を文書化して読ませるのが、いまのところもっとも効きました。

## Stage 5は未実施のまま公開した

この実行は Stage 5（固定diffの独立実装レビュー）を実施せずに公開しています。

姉妹拡張では、Stage 5 で blocker 1件・major 6件が見つかりました。いずれも自動テスト139件を通過した状態ですり抜けていたものです。

- 先頭ラベル除去が最後の区切り記号を採用し、`生年月日：… 登録日：…` で誤った日付を無警告で受理していた（blocker）
- ポップアップの設定読み込みTOCTOUにより、未知のschemaVersionを既定値で上書きし得た
- バッジ `!` を消す経路が無く永久に残っていた

実機スモークテストは Stage 5 の代わりになりません。実機で分かるのは触った経路の症状だけで、Stage 5 が対象とするのは触っていない経路の設計上の欠陥です。上のblockerは、症状が出ないタイプでした。

`state.json` にもそう記録してあります。

```json
"not_done": [
  "Stage 5: 固定diffの独立実装レビュー（2席）",
  "Stage 6: 指摘処理・Test Gate B",
  "実Chromeスモークテスト（実行トレース型監査による代替も未実施）"
],
"note": "Stage 0-4 まで完了。実機で動作確認した者はまだ居ない。"
```

未実施を実施済みに丸めないことが、この種のワークフローでは効きます。工程を定義した以上、飛ばしたなら飛ばしたと書く。書かなければ、次に読む人が、レビュー済みのコードだと誤解します。

## まとめ

- 設計・実装・レビューでセッションを分ける。同じセッションだと自分のコードを自分で承認する
- テストは実行結果で判定する。AIの「通りました」を信じない
- blockerとmajorの対応不要は人間の承認を必須にする
- 査読席には流用元の実コードまで読ませる。設計書だけでは設計と実装の乖離が出ない
- 自動テストは要件の写しである。要件が間違っていれば間違いごと固定される
- 同じ種類のミスは繰り返す。パターン集を作って毎回読ませる
- 飛ばした工程は飛ばしたと書く
