# 検討テーマ

**次に作る自作アプリと、それを売るマーケットの選定。**

具体的には以下2点を検討せよ。

1. **Google Playなど既存のマーケットで公開できて、短期間で作れて、実際に需要がありそうな自作アプリ案を20〜30個出す。**
   各案について「誰のどんな手作業を減らすか」「公開先マーケット」「収益化の方法」「実装規模」「主なリスク」を明記する。
2. **「売れるマーケット」の選定。** Google Playを主戦場にする案が本人の中で有力だが、それが妥当か。Microsoft Store・App Store・Chrome Web Store（用途限定）・その他をどう使い分けるか。あわせて、Google Play案の前提（15年前の開発者アカウントの再利用、Web技術で作った中身をAndroidアプリとして出す方法）が成立するかを検証する。

# 依頼者からの背景情報（原文をほぼそのまま収録）

## 現状

- 自分でかなり幅広いアプリを作れる状態になってきた。
- 実装そのものより、要件定義・設計・AIを使った開発・自動化のノウハウが蓄積している。
- 今後は「特定の1アプリに全振り」ではなく、受託案件・自作アプリ・Chrome拡張・記事を並行して、いろいろ試したい。
- 競合がいることはあまり気にしていない。短期間で競合相当のものを作れるので、競合ゼロのアイデア探しにはこだわらない。
- 「AIを使った○○」だけでは商品として弱いと感じている。AIは裏側で使うのはいいが、AI自体を売りにはしたくない。

## 現在進行中の受託案件

イギリス法人向けの営業リード生成ツールを開発中。内容は、Companies Houseの法人データ → 地域・規模・業種などで企業を絞る → 公式サイトを特定 → 登記情報とサイト情報を照合 → 問い合わせフォーム・代表メール・電話番号等を取得 → CSV出力、というもの。

第1段階は完成して動作している。2,135社で実測し、公式サイト特定344社（16.1%）、そのまま営業に使える92社（4.3%）、要確認252社、サイト特定後は87.9%でメールまたは問い合わせフォームを取得、という結果。

第2段階では、Web管理画面・営業テンプレート管理・問い合わせフォームへの自動入力・送信履歴管理・複数人での重複送信防止まで作る予定。送信自体は人が行う設計。

この案件だけに依存せず、今後も同様に色々な開発案件を受けていきたい。

## 自作アプリについて

自作アプリも本格的にやりたい。以前候補に出たもの：価格ウォッチャー／在庫監視／Webページ変更監視／企業リサーチ／AI開発支援／設計書とコードの差分管理。

ただし、価格・在庫監視はみんな考えるが、競合が多いこと自体は問題ではない。一方でAI開発支援系は商品として少し弱く感じる。

なので、もっと直接的に「世の中の人がいまだに手作業でやっていて面倒なこと」を探して、それをアプリ化する方向が面白そう。特に、

- Excelで管理している
- 毎回同じ検索をする
- コピペを繰り返している
- 毎回同じ情報を入力する
- 複数サイトを行き来する
- 手で比較・集計している

みたいな領域を探したい。

## 公開場所について（現在の未決事項）

**Chrome Web Store**：Chrome拡張はすでにかなり作っている（別会合で55案を管理、公開済み5本、実装済み未提出の在庫が多数）。ただし現在は新規公開数の制限がボトルネックになっており、Chromeだけで大量に自作アプリを展開する戦略は厳しい。Chromeは今後「ブラウザ拡張でないと価値が出ないアプリ」に限定する可能性が高い。

**Webアプリ**：作れる。ただし「自分のWebサイトにアプリを並べて、SEOやSNSでゼロから集客する」方式は本人としては現実的ではないと判断。「どこに置くか」より、既にユーザーが存在するマーケットで公開したい。

**Android**：約15年前にAndroidアプリを開発していた経験あり。当時Google Playの開発者登録料も払っているはずなので、昔のPlay Consoleアカウントが生きていれば再利用できる可能性がある。そのため現在、Google Playを自作アプリの新しい主戦場にする案がかなり有力。Web技術で中身を作ったとしても、最終的にAndroidアプリとしてGoogle Playへ出す方法も検討できる。

**その他候補**：Google Play／Microsoft Store／App Store／Chrome Web Store（用途限定）など。

## 今やりたいこと

まずは自作アプリのアイデアを大量に出したい。条件は、

- 競合の有無はあまり気にしない
- AIありきにしない
- 実際に誰かの面倒を減らす
- 小さく作れる
- 短期間で公開できる
- 課金・広告など収益につなげられる
- できればストア内検索など、既存の集客導線がある
- 1本に半年かけるより、複数出して反応を見る

という方向。受託で現金を作りながら、自作アプリを何本も投げて、当たったものを育てる戦略を考えている。

# 論点整理（Stage 0・議長）

## 検討の目的（何が決まれば成功か）

1. 次の3か月で着手候補にできる自作アプリ案が20〜30件、比較可能な形（同じ項目で記述）で揃うこと。
2. 主戦場とするマーケットが、根拠つきで1つに決まること（Google Play案の採否）。
3. 「複数出して反応を見る」戦略を実際に回すための運用条件（同時本数・撤退基準・収益化の型）が決まること。

## 制約

- **人員**：個人開発者1名。受託案件と並行するため、自作アプリに使える時間は限られる（具体的な時間数は不明。週数時間〜十数時間と仮定）。
- **開発規模**：1本あたり「小さく作れて短期間で公開できる」こと。目安として実装〜公開まで1〜2週間程度を想定（依頼者の明示ではなく議長の仮置き。異論があれば示せ）。
- **方針**：AIを売りにしない（裏側での利用は可）。競合の有無は選別軸にしない。自前サイトでのSEO/SNS集客は前提にしない。
- **Chrome Web Store**：新規公開数の制限があり、主戦場にはできない。「拡張でないと価値が出ないもの」に限定。
- **Google Play**：15年前のアカウントの生死は未確認。2023年以降の新ポリシー（個人アカウントのテスト要件、本人確認、住所公開、非アクティブアカウント整理など）が旧アカウントにどう適用されるかも未確認。
- **法務**：日本在住の個人開発者として、有料アプリ・アプリ内課金・広告に伴う表示義務（特定商取引法、プライバシーポリシー、ストアの開発者情報公開）を満たす必要がある。

## 判定基準（裁定で重視する観点）

- **目的適合性**：「誰かが手作業でやっている面倒」を直接減らすか。AIを売りにしていないか。
- **制約充足**：小さく作れるか。選んだマーケットの審査・ポリシーを通せるか。個人1名で運用できるか。
- **根拠の強さ**：需要の裏付け（ストア内検索で探されている、有料の競合が存在する、既存の手作業が観測できる）があるか。マーケット選定の前提を一次情報で確認しているか。
- **リスク**：ストアポリシー・法務・プラットフォーム依存・収益化手段の実現性が具体的に評価されているか。
